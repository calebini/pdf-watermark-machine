# Deploy the browser utility

## GitHub Pages

The existing project can host this static utility. On GitHub Free, Pages needs
a public repository. Before changing visibility, finish the repository cleanup,
including its previous Git history, repository name and build artifacts.
No site has been deployed yet.

1. Publish the reviewed source and Pages workflow to the repository's `main`
   branch. The workflow is `.github/workflows/pages.yml`.
2. In GitHub, open **Settings > Pages** and choose **GitHub Actions** as the
   build/deployment source.
3. Open **Actions > Browser utility — GitHub Pages > Run workflow** and run it
   on `main`. Later changes to `web/` on `main` also deploy automatically.
4. After the workflow succeeds, follow its `github-pages` environment URL.
   Use this URL rather than constructing one from an old repository name.
5. Generate a copy from a clean local PDF and inspect the downloaded result.

The build uses a hosted Linux runner and Node 24, installs pinned dependencies,
runs the unit checks, builds and publishes only `web/dist/`. No API token or
application secret needs configuring: the deployment job uses GitHub's built-in
job token and OIDC permissions. The website is public and has no sign-in.
Templates, customer names and generated PDFs are processed only in the browser.
Relative asset paths support the repository's Pages subdirectory.

The fuller browser/PDF tests in README.md were run locally; the deployment
workflow runs the Node unit checks. Native desktop builds remain separate.

For a Pages-only source distribution, use the static ZIP generated by
`scripts/package_web.py`. Publish its files through a Pages pipeline; do not
upload templates or generated PDFs to the repository.

[GitHub Pages workflow documentation](https://docs.github.com/en/pages/getting-started-with-github-pages/using-custom-workflows-with-github-pages)

## GitLab Pages alternative

The repository also includes a GitLab Pages build.
Keep the current repository layout: the root `.gitlab-ci.yml` includes
`web/gitlab-pages.yml`, which builds only the browser utility.

## Set up in GitLab

1. Create a **blank private project**, for example `pdf-watermark`, in your
   chosen GitLab group. Leave repository initialization unchecked when pushing
   this existing repository. Your account needs permission to push and manage
   project settings. Copy the project's SSH or HTTPS clone URL.
2. Enable Pages and restrict the website: **Settings > General > Visibility,
   project features, permissions > Pages > Only project members**. Save this
   before the first deployment. Private repository visibility alone is not the
   website access setting. Add the colleagues who should use the tool as project
   members (Guest or higher is enough for Pages access).
3. Under **Settings > CI/CD > Runners**, ensure a Linux runner is available to
   this project. The supplied job is untagged and uses `node:24-alpine`; it needs
   a Docker/Kubernetes executor, or an equivalent runner supporting this image.
   If your runner requires tags, add your administrator's tags to `deploy-pages`
   in `web/gitlab-pages.yml`. The build needs access to the Node image registry
   and the npm registry (or your company's configured mirrors).
4. Push this project, including the new `web/` source and root `.gitlab-ci.yml`,
   to the GitLab project's default branch. Keep the existing GitHub remote;
   GitLab can be added as a separate remote once its URL is known. Templates,
   customer outputs, local dependencies and build artifacts stay excluded.
5. Follow the job in **Build > Pipelines**. When it succeeds, open **Deploy >
   Pages** to get the published HTTPS address.

On **GitLab.com**, hosted Linux runners are available subject to your account's
verification, compute quota and group settings. On a **company GitLab server**,
ask the administrator to confirm Pages, Pages access control, HTTPS, and a
compatible runner are enabled. This configuration uses GitLab 17.9+ syntax;
older servers need an adjusted pipeline. A custom domain is optional.

No application API keys, owner-password variables, database, Python installation
or native qpdf installation are required on GitLab or colleagues' computers.
GitLab's existing CI job credentials handle deployment. Users need a current
browser with WebAssembly, JavaScript and downloads enabled, plus their GitLab
sign-in when Pages access control is on. Chrome and Edge were tested locally.

## What the pipeline does

On the default branch it runs `npm ci`, `npm test`, and `npm run build` in `web/`,
then publishes only `web/dist`. The build includes JavaScript, WebAssembly, the
font and license notices. It contains no template or generated customer PDF.
Relative asset URLs support either a project subdirectory or a dedicated Pages
domain. Node unit checks run in CI; the fuller browser/PDF checks described in
README.md were run locally and are not part of this deployment job.

At runtime the static host serves the application; PDFs and customer names stay
in the user's browser. Each output gets a fresh random owner password and qpdf
encryption key, with the same declared PDF permissions as the local preview.
No shared encryption secret needs configuring on the host.

## Verify the first deployment

1. Open the HTTPS Pages address while signed in as an allowed project member.
   Confirm the form loads without JavaScript, worker, font or WASM errors.
2. Open it in a private/incognito window. It should require GitLab sign-in and
   refuse access to a user who is not a project member.
3. Select a clean local template, generate a test customer copy, and inspect its
   header, watermark, page count and PDF permissions in an approved PDF reader.
   Source watermarks remain, so use the template without placeholder names.

If Pages is absent from settings, ask the GitLab administrator to enable it.
If a job is stuck pending, check runner availability, required tags and quota.
If dependency downloads fail, check the runner's registry/mirror access.
